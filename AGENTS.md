# Инструкции для ИИ

Правила действуют для всего репозитория. Общайся с пользователем на русском. Если требование, контракт или архитектурное решение неоднозначны — спрашивай, не угадывай.

## Карта проекта

Это backend Lumosapp: NestJS-монорепозиторий с двумя приложениями и общими контрактами.

| Путь                     | Ответственность                                                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `apps/main`              | HTTP API: пользователи, авторизация, сессии, посты; PostgreSQL через Prisma; взаимодействие с файловым сервисом              |
| `apps/files`             | Загрузка, обработка и удаление файлов; Sharp для изображений, S3 для объектов, MongoDB/Mongoose для данных файлового сервиса |
| `libs/contracts`         | Общие контракты файловых операций; публичные экспорты через `index.ts`                                                       |
| `apps/main/prisma`       | Prisma-схема и миграции основного приложения                                                                                 |
| `apps/main/test`         | Тесты основного приложения, включая HTTP e2e                                                                                 |
| `docs/superpowers/specs` | Согласуемые решения и требования                                                                                             |
| `docs/superpowers/plans` | Планы реализации; наличие плана не означает, что код уже реализован                                                          |

Основные бизнес-модули находятся в `apps/main/src/modules/user-accounts` и `apps/files/src/modules/files`. Пользователи и посты сейчас принадлежат одному модулю main: не создавай новые границы модулей без необходимости задачи.

Main создаёт Post с null-позициями и сохраняет отдельное событие с исходными байтами каждой фотографии в PostgreSQL outbox, затем возвращает `201 { postId }`. Scheduler публикует исходники через RabbitMQ; consumer files только валидирует и сохраняет MongoDB inbox до ack. Scheduler files проверяет отмену, сохраняет изображение (и preview для index=0), создаёт неизменяемый outbox результата и завершает inbox. Scheduler outbox files ждёт publisher confirm. Consumer main сохраняет результат до ack; scheduler заполняет только пустую позицию Post и preview, пропускает отсутствующий пост, отправляет SSE при переходе в READY.

Все четыре хранилища событий используют `UNPROCESSED`, `PROCESSING`, `OK`, `ERROR`: 3 попытки, пауза 10 секунд, восстановление PROCESSING старше минуты каждые 10 секунд. Обработка раз в секунду, до 10 событий параллельно, без локального перекрытия запусков. Через час завершённые события очищаются до ID и статуса; повтор не изменяет даже очищенную запись. UUID назначается в main и сохраняется через `messageId` / `eventId`; ключ — `eventId` в PostgreSQL и строковый `_id` в MongoDB. Исчерпание попыток не удаляет Post и не создаёт FAILED. Отдельных jobs, транзакций и распределённых блокировок нет; один экземпляр каждого сервиса.

RabbitMQ обслуживается только `@golevelup/nestjs-rabbitmq`. TCP сохраняется для отмены `cancel-post-images` с `{ postId }`, удаления `delete-files` и остальных файловых операций. Действующий поток, ограничения и переход описаны в [2026-09-19-durable-image-events-design.md](docs/superpowers/specs/2026-09-19-durable-image-events-design.md). Сбой между созданием Post и сохранением всех исходников остаётся принятым ограничением отсутствия транзакции; после ERROR и очистки байты автоматически не восстановить.

## Паттерны и размещение кода

Ориентир для нового кода — существующие слои модуля:

- `api`: контроллеры, DTO, guards, decorators, mappers, view types. Контроллер принимает запрос и передаёт выполнение через `CommandBus`/`QueryBus`; бизнес-правила размещай в application.
- `application/use-cases`: изменяющие операции. Команда описывает входные данные, `@CommandHandler` и `execute` реализуют сценарий.
- `application/query-handler`: обработчики чтения. Возвращай согласованный view type; преобразование результата размещай в mapper.
- `application`: сервисы и factories для логики, используемой сценариями.
- `infrastructure/repositories`: доступ к данным. Используй существующие repositories и `PrismaService`, не переноси запросы к БД в контроллеры.
- `core`: общие для приложения adapters, ошибки и инфраструктурные компоненты. Не складывай сюда произвольную бизнес-логику.
- `libs/contracts`: переиспользуемые межсервисные контракты. При изменении контракта проверь обе стороны по исходникам, включая поля, nullable-значения и ошибки.

Примеры для навигации:

- Контроллер и CQRS: `apps/main/src/modules/user-accounts/api/auth.controller.ts`.
- Команда и use case: `apps/main/src/modules/user-accounts/application/use-cases/posts-use-cases/create-post.use.case.ts` — существующее имя файла нестандартное; для нового кода используй правило ниже.
- Repository: `apps/main/src/modules/user-accounts/infrastructure/repositories/post-repositories/posts.repository.ts`.
- Mapper: `apps/main/src/modules/user-accounts/api/mappers/auth.mapper.ts`.
- Обработка изображений: `apps/files/src/modules/files/application/image-processing.service.ts`.
- Внешнее хранилище: `apps/files/src/core/adapters/s3.adapter.ts`.

### Ошибки, валидация и контракты

- В main используй `DomainExceptions`, существующие `ErrorStatus` и `DomainExceptionFilter` из `apps/main/src/core/exceptions`. Не вводи параллельный формат ошибок.
- Настройка HTTP приложения находится в `apps/main/src/setup/app-setup.ts`: маршруты без глобального префикса, глобальная валидация DTO и фильтр ошибок. Swagger доступен по `/docs`.
- HTTP DTO, view types и межсервисные контракты имеют разные назначения. Не возвращай модель БД вместо публичного ответа без явного преобразования.
- При изменении HTTP-контракта согласуй DTO, mapper/view type и Swagger. Проверяй авторизацию и принадлежность ресурса в самом сценарии, а не только наличие guard.
- Конфигурацию получай через существующие config-компоненты приложения. Секреты и содержимое `.env` не выводи в логи, ответы или документацию.

## Единый нейминг

Имена в коде — на английском. Файлы и каталоги — `kebab-case`, классы и типы — `PascalCase`, функции, методы и переменные — `camelCase`. Для констант уровня модуля и DI-токенов используй `UPPER_SNAKE_CASE`, как `FILES_TCP_CLIENT`.

| Назначение             | Файл                              | Символ                                                  |
| ---------------------- | --------------------------------- | ------------------------------------------------------- |
| Use case               | `create-post.usecase.ts`          | `CreatePostUseCase`                                     |
| Команда этого сценария | В том же `create-post.usecase.ts` | `CreatePostCommand`                                     |
| Query handler          | `profile-query-handler.ts`        | Следуй именованию query/handler в соседних обработчиках |
| Контроллер             | `auth.controller.ts`              | `AuthController`                                        |
| Сервис                 | `auth-session.service.ts`         | `AuthSessionService`                                    |
| Repository             | `posts.repository.ts`             | `PostsRepository`                                       |
| DTO                    | `create-post.dto.ts`              | `CreatePostDto`                                         |
| Mapper                 | `auth.mapper.ts`                  | `AuthMapper`                                            |
| Тип ответа             | `profile-view.type.ts`            | `ProfileViewType`                                       |
| Adapter                | `s3.adapter.ts`                   | `S3Adapter`                                             |
| Unit-тест use case     | `create-post.usecase.spec.ts`     | Название проверяемого сценария в `describe`             |

Для всех новых use case файлов обязателен суффикс `.usecase.ts`. Не используй `.use.case.ts`, `-use.case.ts` или запятую вместо точки. Существующие несовпадения не являются образцом; массовое переименование выполняется отдельной задачей.

Проект использует ESM и `nodenext`: в относительных TypeScript-импортах сохраняй расширение `.js`, как в существующем коде. Форматирование задаёт `.prettierrc`: одинарные кавычки и trailing commas.

## Тестирование

- Покрывай важную бизнес-логику: права и принадлежность ресурса, ограничения входных данных, переходы состояний, истечение сроков, повторное выполнение и обработку ошибок, когда они относятся к изменению.
- Проверяй наблюдаемый результат и инварианты, а не повторение строк реализации. Для исправления ошибки добавляй проверку сценария, который её воспроизводит.
- **Не пиши тесты обращений одного микросервиса в другой:** доставки TCP/RabbitMQ-сообщений между приложениями, транспорта и простого делегирования в клиент. В тестах бизнес-сценариев подменяй межсервисную границу и проверяй локальный результат при успехе или ошибке зависимости.
- Не добавляй тесты пустых конструкторов, тривиальных getters и простых wrappers ради покрытия. Изменения только документации не требуют программных тестов.
- Проверки данных и транзакционных инвариантов проводи на изолированной локальной БД, если mock не может доказать нужное поведение. Внешние сервисы и реальные окружения без согласования не используй.
- Запускай проверки, относящиеся к изменённому коду. Если проверка не запустилась или упала, сообщи причину; не выдавай статическую проверку за успешный runtime-тест.

## Команды и проверки

Команды выполняются из корня; актуальные scripts находятся в `package.json`.

| Задача                                     | Script                           |
| ------------------------------------------ | -------------------------------- |
| Разработка main                            | `pnpm run start:dev:main`        |
| Разработка files                           | `pnpm run start:dev:files`       |
| Сборка main                                | `pnpm run build:main`            |
| Сборка files                               | `pnpm run build:files`           |
| Unit-тесты                                 | `pnpm run test`                  |
| HTTP e2e main                              | `pnpm run test:e2e`              |
| Покрытие                                   | `pnpm run test:cov`              |
| Генерация Prisma client для локального env | `pnpm run prisma:generate:local` |

`test` содержит `--passWithNoTests`: успешный exit code без найденных тестов не доказывает покрытие. Проверяй количество выполненных тестов. `lint` содержит `--fix` и изменяет файлы; не запускай его как read-only проверку всего репозитория. `format` указывает корневые `src`/`test`, поэтому не считай его форматированием всего монорепозитория. Миграционные scripts содержат фиксированные имена и выбор окружения: перед запуском прочитай script и проверь целевую БД.

## Работа ИИ с репозиторием

- Перед изменениями проверь текущую ветку и `git status`. Сохраняй чужой WIP и не включай несвязанные изменения в задачу.
- Не делай попутные обновления библиотек, массовые переименования или рефакторинги. Новые архитектурные решения согласуй с пользователем.
- Не редактируй сгенерированный Prisma client вручную. Меняй источник схемы и используй генерацию.
- Различай существующий код, планируемую реализацию и непроверенные предположения. При расхождении плана с явными указаниями пользователя следуй указаниям пользователя и обозначь расхождение.
- Коммит, push и развёртывание выполняй по явному запросу. В результате отдельно сообщай изменения и выполненные проверки.

### CodeGraph

Для структурных вопросов сначала используй доступные `codegraph_*` инструменты: определения, callers/callees, связи, влияние изменений и обзор области. Если сервер предоставляет только `codegraph_explore`, передавай туда вопрос или несколько связанных имён/путей одним запросом.

Не делегируй отдельному агенту повторное чтение кода для архитектурного объяснения. Обычно достаточно focused context и одного пакетного explore. Не перепроверяй результаты CodeGraph через grep. Native search/read используй для строк, комментариев, конфигурации, документации и деталей, которых нет в результате. Если CodeGraph сообщает об устаревших данных, учитывай перечисленные несинхронизированные файлы; сразу после правки дождись синхронизации индекса.

Если индекс не инициализирован, спроси пользователя: «В проекте не инициализирован CodeGraph. Запустить `codegraph init -i` для построения индекса?» Не запускай инициализацию самовольно. Если инструменты недоступны, обозначь это и используй обычный поиск.

### Context7

Для вопросов о библиотеках, фреймворках, SDK, API, CLI и облачных сервисах используй Context7, включая синтаксис API, настройку, миграции версий и библиотечные ошибки. Сначала `resolve-library-id` с названием и вопросом, затем `query-docs` с выбранным ID и полным вопросом. Если пользователь уже дал точный ID вида `/org/project`, повторное разрешение не требуется. Выбирай совпадение по названию, релевантности, репутации источника и версии; при плохом результате уточни запрос.

Для документации библиотек предпочитай Context7 веб-поиску. Он не требуется для рефакторинга, бизнес-логики, code review, самостоятельных скриптов и общих концепций программирования. Если Context7 недоступен, сообщи об ограничении; не утверждай, что документация проверена.
