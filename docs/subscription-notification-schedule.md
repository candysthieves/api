# Расписание уведомлений подписки

Payments вычисляет сроки из сохранённых дат оплаты и подписки:

- успешная оплата: `paidAt + 30_000`;
- следующее списание: `nextChargeDate - 86_400_000`;
- окончание подписки: `expirationDate - 86_400_000`;
- окончание через неделю: `expirationDate - 7 * 86_400_000`.

Создаются только события с `executeAt >= paidAt`. При отсутствии следующей даты списания соответствующее
событие не создаётся: это возможно при повторной обработке оплаты после отмены.
Проверка не использует текущее время обработки события.

Для 5 минут создаётся одно уведомление, для суток — три, для 7 суток и более — четыре.
У суточной подписки напоминания об окончании и о списании наступают в момент оплаты,
об успешной оплате — через 30 секунд.

## Redis и отмена

Ключ записи без префикса: `<executeAt>:<userId>:<paymentId>:<notificationId>`.
Фабрика передаёт составной ключ в `id`, а сохранённый JSON содержит публичный UUID
в `id`, поля платежа, `executeAt`, `isRead`, `readAt` и `createdAt = executeAt`.
Второй JSON `notification:<UUID>` для запланированного уведомления не создаётся.
В `notifications:schedule:due` хранятся составные ключи со score времени исполнения. Scheduler выбирает до 10 записей
с наступившим сроком раз в секунду. При ошибке scheduler выводит её в консоль
и удаляет ID из очереди. Счётчик попыток и ошибка в записи не хранятся; повторов нет.
Общий индекс `user:<userId>:notifications` содержит полные ключи со score времени
показа. Отдельного индекса `notifications:schedule:user:<userId>` больше нет.
Выдача и счётчик выбирают только записи с наступившим сроком за последние 30 дней.
Scheduler читает тот же JSON и после отправки удаляет только элемент очереди.
Обычные уведомления без расписания сохраняются одной записью `notification:<UUID>`
и включаются в тот же пользовательский индекс.

`ReplacePaymentNotificationsUseCase` перед сохранением удаляет расписания других платежей пользователя с `executeAt > now`,
где `now` передаётся в выборку будущих записей. Метод репозитория `save` только сохраняет запись и индексы. Старые будущие записи удаляются
из Redis и индексов due/user. Расписания с наступившим сроком сохраняются, даже если
scheduler ещё не успел их выполнить. Уже опубликованные уведомления, их UUID,
даты и состояние прочтения сохраняются. Отдельный ключ текущего платежа и проверка
порядка оплат не используются.

Например, при смене 7-дневной подписки на 30-дневную через минуту остаются
два старых уведомления (об оплате и об окончании через 7 дней), удаляются два
будущих напоминания и добавляются четыре новых расписания. Индекс пользователя
хранит как новое расписание, так и старую историю, включая связь с paymentId.

Публичный `notificationId` остаётся отдельным UUID. Повторная обработка события
создаёт отдельное расписание с новым UUID; дедупликации по платежу и типу напоминания нет.
Event ID в outbox/inbox:
`<paymentId>:notification:<title>`, фильтрация и порядок напоминаний не влияют на ID.
При повторной обработке старого платежа ID с числовым индексом и ID с title различаются:
outbox может сохранить новое событие; повторные уведомления допустимы.

Событие отмены передаёт `userId` и `paymentId`. Отмена удаляет все сохранённые
уведомления этого платежа с `executeAt > now` и их индексы, независимо от типа.
Время и платёж извлекаются из ключей без чтения JSON. Записи с наступившим сроком
и опубликованные уведомления сохраняются. Маркер отмены не хранится.

## Переход со старого формата

По согласованию перенос существующих данных не требуется. Старые индексы и записи
новая реализация не преобразует; она рассчитана на новый формат пользовательского
индекса с полными ключами. Рабочая Redis в рамках изменения кода не очищалась.

## Ограничения

Публичные уведомления используют один индекс `user:<userId>:notifications` со score
даты создания. Прочтение меняет только JSON записи. Список и счётчик фильтруют записи
по `isRead`; в выдаче непрочитанные идут первыми, внутри групп — новые первыми.
Формат курсора `unread:<createdAt>` / `read:<createdAt>` сохранён. Он не различает
записи с одинаковой датой на границе страниц. Перенос старых индексов read/unread
не выполняется по согласованию: существующие данные переносить не требуется.

- Порядок доставки уведомлений с одинаковым сроком не гарантируется:
  scheduler обрабатывает записи параллельно с периодом в секунду.
- Разные уведомления с одинаковыми сроками имеют разные ключи благодаря UUID.
  Для выборки расписаний используются индексы due и user; общего префикса записей нет.
- Операции Redis не атомарны. Сохранение, отмена, замена расписания и scheduler
  могут пересечься; сбой между командами может оставить неполную запись или индекс.
- Сбой после доставки до удаления из очереди может вызвать повторную доставку.
- Завершённые расписания не имеют TTL и занимают память.
  Индекс пользователя растёт вместе с историей, поэтому сохранение нового расписания
  со временем требует больше чтений Redis. Отдельный архив и политика хранения не добавлены.
- Существующие списки и счётчик показывают последние 30 дней. Более старые записи
  сохраняются в Redis, но API полной истории ещё нет. Сохранность при перезапуске
  Redis зависит от его настройки persistence; отдельного долговечного архива нет.
- Лимит 10 записей за проход и недоступность сервисов могут задержать отправку.

## Проверки

Unit-тесты фабрики проверяют сроки и состав уведомлений. Интеграционные тесты
репозитория запускаются только с `RUN_NOTIFICATION_REDIS_TESTS=1`, на отдельном
локальном Redis `127.0.0.1:16389`, DB 15; они очищают эту тестовую БД.
