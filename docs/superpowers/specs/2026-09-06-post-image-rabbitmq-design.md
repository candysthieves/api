# Пофайловая обработка изображений поста через RabbitMQ

Дата: 2026-09-06. Основание: согласованные решения в текущем обсуждении.

## Требования

- До 8 картинок в посте; существующий предел одной картинки — 5 * 1024 * 1024 байт.
- Пост видим сразу после создания, без ожидания обработки изображений.
- `images` — массив фиксированной длины в исходном порядке; незавершённая или ошибочная позиция содержит явный JSON `null`. `preview` тоже `null` до готовности.
- `imageProcessing` содержит состояние каждой позиции: `imageId`, `status`, `attempts`, `error`. Статусы: `QUEUED`, `PROCESSING`, `READY`, `FAILED`. Ошибка: `{ code, traceId }`; подробности сохраняются в серверном журнале/БД без исходных байтов и секретов.
- Одна картинка — одно сообщение с исходным бинарным телом. Base64 и JSON-массив байтов не используются. Метаданные передаются через AMQP properties/headers.
- Один активный обработчик изображений; следующая обработка начинается после завершения текущей. Первое изображение и его preview обрабатываются последовательно в одном задании.
- После каждого результата main сохраняет изменение позиции, затем отправляет SSE с данными строго `{ postId }`. Клиент перечитывает пост. Предлагаемое имя нового события: `post-media-updated`; существующее `post-created` используется при создании поста.
- Всего 3 попытки обработки, включая первую. Для задержки повторов план принимает 10 секунд как техническое значение по умолчанию; пользователь согласовал число попыток, отдельного подтверждения интервала не было. Во время задержки обрабатываются другие картинки.
- При частичной отправке пост не удаляется. Принятые задания продолжаются, неподтверждённые/неотправленные позиции получают `IMAGE_DISPATCH_FAILED`. Потеря confirm не доказывает потерю сообщения: поздний успешный результат переводит такую позицию в READY.
- Повторная доставка задания/события не дублирует файлы, не увеличивает массив и не откатывает READY в более раннее состояние.
- Превью производится из картинки с index=0; её READY означает готовность и изображения, и превью.
- Доступа к volume приложения не требуется. Исходники находятся в RabbitMQ; готовые файлы сохраняются существующим S3Adapter. Долговечность очереди требует сохраняемого диска самого брокера: durable/persistent не переживают удаление его данных.

## Проверенный текущий поток

`CreatePostUseCase` создаёт PROCESSING-пост, передаёт весь набор через `FilesTcpClient.uploadPostFiles` с timeout 15 секунд и удаляет пост при ошибке. `PostMediaProcessingService.accept` сохраняет исходники в GridFS; `process` загружает все исходники через Promise.all, затем обрабатывает их последовательно и создаёт единое событие результата. Main принимает событие через RMQ, сохраняет InputEvent, применяет весь массив и подтверждает событие files через TCP. Это установлено по исходникам, причина реального серверного падения по логам не установлена.

## Архитектура

Для нового потока выделяются три durable-очереди с суффиксами `.post-images.v1`, `.post-images.retry.v1`, `.post-images.results.v1`, производными от существующих имён очередей. Это исключает попадание бинарных сообщений в Nest JSON consumer. Используется существующая зависимость amqplib, отдельные confirm publisher channels и consumer channels. Новые зависимости и volume приложения не нужны.

Main создаёт пост и метаданные всех позиций в одной PostgreSQL-транзакции. Изображения хранятся как ранее в JSON; новое nullable JSONB поле `image_processing` хранит согласованный массив состояний плюс внутренние revision/dispatch timestamps. Старые посты с NULL в новом поле отображаются по старым данным и не требуют массового переписывания.

Main отправляет задания последовательно с publisher confirms, mandatory routing и ограниченным временем отправки всего набора (предлагаемое значение 15 секунд, не таймаут обработки). При ошибке прекращает отправку оставшихся байтов, условно отмечает только ещё не начавшиеся позиции ошибкой и возвращает существующий HTTP 201 `{ postId }`. Удаление поста на этом пути убирается. После рестарта main помечает просроченные незавершённые dispatch-позиции ошибкой; позднее событие worker их исправляет. Ни один QUEUED не должен навечно остаться из-за падения main до отправки.

Files запускает отдельный consumer: prefetch=1, noAck=false, queue argument x-single-active-consumer=true. Mongo image job с уникальным imageId содержит попытки, стабильные fileId/previewFileId, прогресс и ожидающее публикации событие. Все изменения одной job атомарны; Mongo replica set для этого не требуется. Файлы сохраняются по стабильным идентификаторам и ключам через идемпотентный метод FilesService, повторное задание использует уже сохранённый результат. Исходное задание подтверждается после записи результата/terminal failure и события в эту job.

Job содержит один pending event: каждое новое событие заменяет старое более свежей полной проекцией состояния изображения. Отдельный relay публикует pending event с confirms, очищает его только условно по eventId. Дубликаты безопасны. Терминальные события никогда не удаляются до подтверждения брокера. Детальная история попыток остаётся в job для дебага; промежуточные SSE не гарантируются.

Для повторов consumer сначала фиксирует retry state с nextAttemptAt, затем подтверждённо публикует те же байты в retry queue и только затем ack исходного сообщения. Отдельный retry-forwarder с prefetch=1 удерживает сообщение до nextAttemptAt, публикует в основную очередь с confirm и затем ack retry delivery. Он не запускает обработку картинок. Это позволяет задержать повтор без занятия основного worker и без ненадёжного перехода через default dead-letter republish. При падении в промежутке возможен дубль, который отсеивается по imageId/attempt в Mongo. В памяти дополнительно может находиться одно retry-сообщение.

Main принимает JSON-события новой result queue и durable upsert-ит существующий InputEvent до ack брокеру. В PostgreSQL-транзакции блокирует Post, проверяет imageId/index/revision, обновляет одну позицию и статус обработки события. Для новых событий TCP acknowledge не вызывается. После commit испускает SSE. Удалённый пост приводит к завершению события без бесконечных повторов; готовые fileId направляются на существующее удаление через сохраняемое задание очистки.

## Состояния и сбои

- Revision worker монотонна для imageId; terminal READY не откатывается. Dispatch failure имеет revision=0, worker события начинаются с 1.
- Attempts — число реально начатых попыток обработки, хранится в Mongo до вызова image processor. Потеря процесса после начала учитывается как попытка; потеря publish результата не расходует попытки обработки.
- Повтор сообщения об уже завершённой job только восстанавливает публикацию terminal event; повторной обработки нет.
- После падения worker во время попытки повторная доставка завершает/повторяет незавершённую работу в пределах 3 попыток; частично сохранённое изображение при неудаче preview переиспользуется.
- Ошибки Mongo/RabbitMQ подтверждения не превращаются в ошибку изображения: сообщение остаётся неподтверждённым, канал закрывается с reconnect/backoff, исключая горячий requeue loop.
- Повреждённое сообщение с известными идентификаторами получает терминальное диагностическое событие. Без валидных идентификаторов — structured error и reject без requeue; оно не блокирует очередь.
- Aggregate mediaStatus: PROCESSING, пока есть QUEUED/PROCESSING; после окончания всех — FAILED при любой ошибке, иначе READY. Публикацию поста этот статус не фильтрует.
- SSE остаётся уведомлением существующего уровня надёжности: состояние БД — источник истины. Пост может быть обновлён до подключения клиента; HTTP GET возвращает последнее состояние.

## Границы

Аватары, удаление/восстановление файлов и старый TCP-контракт сохраняются. Новые посты больше не используют пакетный TCP upload/GridFS. Старый worker нужен для завершения старых заданий; перед включением новой обработки их надо дренировать, чтобы старый и новый worker не конкурировали за ресурсы. Фронтенд не реализуется в этом репозитории. Коммит, push и выкладка не входят в запрос на написание плана.

## Проверка

Unit: wire byte equality, 1/8/9 файлов, состояния/порядок/null, 3 попытки, preview, dedup/revisions, частичная отправка, транзакционное применение событий. Integration на локальных disposable RabbitMQ/PostgreSQL/Mongo/S3 fixture: reconnect, consumer restart, crash windows, lost confirms, broker restart с теми же данными, конкурирующие обновления, удаление поста. Замер локально: один одновременно работающий processor, длина тела равна длине исходника, ограниченная память при серии постов. Реальный сервер не используется без отдельного разрешения.
