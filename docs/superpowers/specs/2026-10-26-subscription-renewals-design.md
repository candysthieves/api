# Автосписания подписок ЮKassa

## Согласованные требования

- Перед первой оплатой проверить последнюю подписку пользователя. При `Processing` отказать в новой покупке существующей ошибкой `PAYMENT_CREATION_FAILED`.
- Каждая ручная покупка создаёт отдельную подписку до вызова провайдера: `Processing`, `lastPaymentId=null`, `expirationDate=null`, provider, tariffId, userId. nextChargeDate первоначально рассчитывается от текущего времени на срок тарифа и уточняется после успешной оплаты. Старой последней подписке установить nextChargeDate=null, сохранив её статус и expirationDate.
- Раз в минуту выбирать последнюю подписку среди всех подписок пользователя и только затем применять `Done`, `YOOKASSA`, `expirationDate <= now`, `nextChargeDate IS NOT NULL`.
- Перевести выбранную подписку в `Processing`, найти последний платёж по `lastPaymentId`, взять сохранённый `paymentMethodId`. При отсутствии способа оплаты оставить `Processing` до таймаута — явное уточнение пользователя.
- После сохранения платежа записать его внутренний ID в subscriptions.lastPaymentId. При автосписании сначала прочитать paymentMethodId старого платежа, затем сохранить новый pending-платёж и заменить lastPaymentId до запроса в ЮKassa. ЮKassa получает `payment_method_id`, `capture=true`, ключ идемпотентности — ID новой попытки. Ответ сохраняет externalPaymentId. Результат применяется существующим webhook/inbox потоком.
- Отдельный scheduler раз в минуту переводит подписки в Processing в Failed, если `coalesce(expirationDate, createdAt) < now - 15 минут`. Для первой оплаты отсчёт от createdAt, для автосписания — от expirationDate. Отдельное время начала обработки не хранится.
- Поздний успешный webhook восстанавливает `Done` даже после `Failed`. Для этого допускается запрос ЮKassa для локально `canceled`/`failed` платежа и переход платежа в `succeeded`.
- При успехе первая оплата заполняет expirationDate от сохранённого paymentDate на срок тарифа; автосписание прибавляет срок тарифа к прежней expirationDate. nextChargeDate получает ту же новую дату, если автопродление не отменено. Для старого succeeded-платежа без paymentDate резервной точкой служит текущее время обработки.
- Webhook находит подписку по lastPaymentId. Обновление дат и статуса разрешено только из Processing/Failed и при совпадении lastPaymentId; повтор для Done не меняет даты. Затем сохраняется существующее событие payment.completed. Main сохраняет Business и отправляет прежний SSE.
- Не добавлять транзакции, распределённые блокировки, новый транспорт, автоматические повторные списания после ошибок или новые события отказа. Гонки с ручной покупкой/отменой и остальные обсуждённые риски пользователь принял.

## Данные и совместимость

ClickHouse subscriptions: nullable lastPaymentId и expirationDate, status Processing/Done/Failed, nullable provider для старых записей без известного платежа. Для существующих подписок status=Done, provider восстанавливается по последнему платежу, неизвестный provider не допускает автосписание.

Для установок, где миграция 20261026060000 уже была выполнена с non-nullable expiration_date, добавлена отдельная 20261026070000_fix_nullable_subscription_expiration.sql. Она меняет тип на Nullable(DateTime), исправляет нулевой срок в Processing/Failed на NULL и возвращает ошибочно Failed в Processing только для подписок не старше 15 минут с pending-платежом или без привязанного платежа. Подтверждённая отмена и настоящий таймаут не сбрасываются. Исправление проверяется на воспроизведённой старой схеме, а не только на чистой установке.

Payments: nullable externalPaymentId до ответа провайдера. Колонки subscriptionId и isRenewal удалены из предлагаемой схемы по указанию пользователя. Связь хранится только в subscriptions.lastPaymentId. Сумма в БД остаётся в центах USD, конвертация в RUB использует существующую фабрику.

Повтор одного успешного платежа не продлевает даты второй раз, пока lastPaymentId указывает на него. Outbox использует существующий payment.id. Порядок последних подписок: createdAt DESC, id DESC для одинакового времени.

После замены lastPaymentId webhook старого платежа больше не найдёт подписку — это согласованное ограничение. Обработчик возвращает SUBSCRIPTION_NOT_FOUND в существующий механизм retry inbox, не создаёт новую подписку и не выбирает другую по userId. Платежи до миграции обрабатываются только при наличии соответствующего lastPaymentId.

## Проверки и ограничения

Unit: создание, запрет Processing, автосписание, отсутствующий способ оплаты, сбои БД/провайдера, поздний успех, отказ, восстановление outbox. Реальные SQL и миграция — в новой изолированной локальной БД. Без реальных платежей и применения миграций к рабочей БД; без commit/push/deploy.

Сбой после принятия запроса ЮKassa до сохранения externalPaymentId остаётся ограничением: автоматический поиск потерянного ответа и повтор запроса не добавляются. Scheduler истечения pending-платежей сохраняет существующее расписание (каждые 30 минут, возраст 15 минут); новый scheduler подписок от него независим.
