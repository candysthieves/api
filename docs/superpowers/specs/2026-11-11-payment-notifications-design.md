# Отложенные уведомления подписки

> Историческое решение. Правила создания, хранения и отмены заменены
> [новым расписанием уведомлений](../../subscription-notification-schedule.md).

Согласовано в диалоге: payments сохраняет четыре отдельных события в существующий outbox. Notifications доверяет контракту, создаёт четыре записи Redis, включая даты в прошлом. Поле разрешения исполнения называется `enabledToExecute`.

Сроки: paidAt + 30 секунд; nextChargeDate - сутки; expirationDate - сутки; expirationDate - 7 суток. При nextChargeDate = null запись о списании сохраняется с executeAt = null и enabledToExecute = false. При отключении автопродления запись остаётся, но enabledToExecute становится false. При новой успешной оплате старое расписание пользователя заменяется. Смена тарифа применяется после успешной оплаты.

Уточнение для коротких подписок: если executeAt < paidAt, запись сохраняется с enabledToExecute = false. Сравнение идёт с датой оплаты, а не со временем доставки события: задержка outbox не должна отключать подходящее уведомление. Для подписки на 5 минут три напоминания отключены, уведомление об оформлении разрешено и появляется через 30 секунд.

enabledToExecute обозначает разрешение уведомления, а executedAt — завершение исполнения. Успешное исполнение и исчерпание попыток доставки не меняют enabledToExecute, чтобы уже сохранённое актуальное уведомление оставалось в списке. Повторное исполнение предотвращают executedAt и attempts. Список (непрочитанные и прочитанные) и counter проверяют enabledToExecute у связанной записи расписания; отключённые записи исключаются даже при наличии публичной записи. Обычные уведомления без расписания сохраняют прежнее поведение. Фильтрация выполняется до ограничения размера страницы, чтением пачками по 100 записей.

Расписание хранится отдельно от публичного списка, чтобы будущие и отключённые уведомления не отображались раньше срока. Scheduler раз в секунду выбирает executeAt <= now. Он сохраняет уведомление в публичном списке независимо от присутствия пользователя. WebSocket используется только онлайн, без ожидания подключения.

Main не подключается к Redis. Gateway передаёт userId и socket.id через NotificationsTcpService в микросервис notifications по TCP: save-notification-session сохраняет или продлевает соединение, remove-notification-session удаляет его. Обе команды принимают { userId, socketId } и возвращают ObjectResult с { success: true }. Только notifications выполняет команды Redis через свой REDIS_CLIENT. Для пользователя разрешено одно соединение в namespace /notifications: новое прошедшее аутентификацию подключение отключает предыдущее через disconnect(true). Main хранит текущий socketId в памяти и последовательно передаёт изменения соединения одного пользователя в notifications, чтобы завершение старой регистрации не перезаписало новую. Redis хранит строку socketId по ключу notifications:socket:<userId>; прежние наборы notifications:sessions:<userId> больше не читаются и истекают по TTL. Срок актуальности связи 90 секунд, обновление каждые 30 секунд и удаление при disconnect сохранены. Удаление проверяет совпадение socketId. Notifications передаёт в main { userId, socketId, notification }; main проверяет принадлежность и актуальность сокета перед emit. Ограничение рассчитано на один экземпляр main и относится к соединениям уведомлений; HTTP-сессии авторизации не отзываются.

События имеют постоянные ID на основе paymentId и title. Новое расписание заменяет старое один раз; запоздавшие события старой оплаты игнорируются по paidAt, при равенстве по paymentId. Отмена помечает subscriptionId, чтобы позднее создание не включило списание снова. По уточнению пользователя логика репозитория расписания перенесена из Lua в TypeScript и выполняется обычными командами ioredis без WATCH, транзакций и блокировок. Проверки повторов и состояния сохранены для последовательных вызовов; одновременные изменения могут перезаписывать друг друга, а ошибка между командами может оставить частично обновлённые данные. Один экземпляр каждого сервиса.

Повтор TCP после сбоя может повторно отправить WebSocket-событие с тем же notification.id. Подтверждение TCP не означает подтверждения фронтом. Уже начавшуюся отправку нельзя отозвать. Redis настроен с AOF everysec и noeviction: авария может потерять последние записи; заполнение памяти приводит к ошибкам записи.

Публичное событие WebSocket: notifications:new, payload { data: NotificationItemContract, error: null }. Main использует существующие NOTIFICATIONS_TCP_HOST и NOTIFICATIONS_TCP_PORT; Redis-конфигурация ему не требуется. Параметры notifications: REDIS_HOST, REDIS_PORT, REDIS_PASSWORD, MAIN_TCP_HOST, MAIN_TCP_PORT. Секреты не включаются в документацию.

## Настройка и эксплуатация

- Доступ к Redis имеет только notifications; main выполняет операции с соединениями через TCP-сервис notifications. При ошибке первоначальной регистрации main отключает сокет; ошибка продления или удаления логируется, запись ограничена сроком активности.
- Notifications подключается к MAIN_TCP_HOST:MAIN_TCP_PORT; по умолчанию 127.0.0.1:4004. Адрес должен быть доступен из notifications и совпадать с TCP-сервером main.
- Redis уже присутствует в docker-compose.yml. Секретные env-файлы и реальные окружения при реализации не изменяются. Обновлять сначала notifications, затем payments: consumer сохраняет поддержку старых payment.completed/payment.canceled, новые оплаты используют четыре payment.notification.scheduled.
- На каждую запись scheduler допускает три ошибки доставки с интервалом 10 секунд. После исчерпания запись удаляется из очереди исполнения, attempts = 3 и lastError сохраняются; публичное уведомление остаётся в списке. Отсутствие онлайн-соединений считается нормальным завершением.
- При повторной отправке после сбоя фронт может получить тот же notification.id. Для отображения без дублей следует использовать этот ID.
- Отмена останавливает будущее исполнение и скрывает отключённое напоминание из списка и counter. Записи в Redis остаются. При замене расписания удаляются четыре старые записи этой схемы, включая их публичные записи, если они уже были показаны.
- События с одинаковым paidAt разрешаются по paymentId; UUID не задаёт реальный порядок оплат в одну миллисекунду. Для строгого порядка таких оплат понадобится отдельная версия подписки.

## Проверка Redis

Бизнес-тесты репозитория запускаются только с RUN_NOTIFICATION_REDIS_TESTS=1 и используют отдельный Redis 127.0.0.1:16389, базу 15. Перед каждым тестом эта база очищается. Нельзя назначать этот порт рабочему Redis при запуске этих тестов. В данной реализации использован временный контейнер lumos-notification-schedule-test без дискового тома.

Программные проверки не заменяют проверку развёртывания: сквозной обмен RabbitMQ/TCP между приложениями не тестировался согласно правилам проекта.

Первичная проверка реализации: 49 тестов в 6 suites прошли, сборки main/payments/notifications успешны. После уточнения для пятиминутной подписки прошли 39 релевантных тестов в 4 suites, включая 10 проверок на изолированном Redis. Проверки межсервисного транспорта не добавлялись. Внешние окружения не использовались.
