# Сохранение изображений через outbox/inbox

Действующий поток заменяет решение от 2026-09-08. Один экземпляр main и files; PostgreSQL и standalone MongoDB, без транзакций, отдельных jobs и распределённых блокировок.

## Поток

```text
Post + OutputEvent main → RabbitMQ → input_events files
  → обработка / S3 / сведения о файлах MongoDB → output_events files
  → RabbitMQ → InputEvent main → заполнение Post → SSE
```

1. Main сохраняет Post с null-позициями и отдельное событие для каждого исходника. Возвращает `201 { postId }` только после сохранения всех событий. При ошибке пытается удалить Post и пометить уже записанные UNPROCESSED-события ERROR; исходная ошибка возвращается HTTP-клиенту. Компенсации независимы, их ошибки логируются.
2. Scheduler main публикует сохранённый Buffer с неизменным UUID в `messageId`. Только publisher confirm разрешает OK. Ошибка публикации не удаляет Post.
3. Consumer files валидирует метаданные, UUID и размер бинарного тела; сохраняет inbox до ack. Некорректное сообщение получает `Nack(false)`, ошибка сохранения — `Nack(true)`.
4. Scheduler files сначала ищет outbox по тому же UUID. Если результат существует, включая очищенный, повторной обработки нет. Иначе проверяет отмену, сохраняет изображение и preview для индекса 0 через существующий FilesService. Перед записью результата проверяет актуальность попытки. Создание outbox использует только `$setOnInsert`; существующие данные и статус не изменяются. Отменённый inbox завершается OK без обработки.
5. Scheduler outbox files публикует результат с исходным UUID в `eventId` и `messageId`, ждёт confirm и завершает событие. Consumer main сохраняет проверенный результат до ack. Scheduler main заполняет только null-позицию и пустой preview. Отсутствующий Post — успешный пропуск. SSE `post-media-updated` с `{ postId }` отправляется при переходе Post в READY.

Размеры изображений положительные числовые. TCP отмены (`cancel-post-images`, `{ postId }`), её существующий срок и другие файловые операции сохранены. Контракт результата допускает только READY с обязательным image; для индекса 0 обязателен preview, для остальных preview равен null. Сообщения FAILED отклоняются валидатором без повторной постановки. Исчерпание попыток сохраняет ERROR в хранилище событий и не удаляет Post.

## Хранение и попытки

Единственный ключ — `eventId` / PostgreSQL `event_id` и MongoDB `_id` (строка). Новые события используют UUID, назначенный main. Исходники хранятся отдельно от JSON: `body bytea` и `body Buffer`; метаданные содержат postId, индекс, исходное имя, MIME и размер. У результата байтов нет.

Активная запись хранит данные, статус, attempts, processingStartedAt, nextAttemptAt, completedAt, lastError и createdAt. Служебные поля допускают отсутствие/null. Повторная доставка не изменяет запись, даже после очистки.

- Каждую секунду каждый обработчик выбирает до 10 доступных событий и выполняет их параллельно. Cron `waitForCompletion` и локальный guard хранилища запрещают перекрытие проходов.
- Переход UNPROCESSED → PROCESSING увеличивает attempts. Всего 3 попытки, включая первую.
- Ошибка при attempts < 3 возвращает UNPROCESSED с nextAttemptAt через 10 секунд. Третья ошибка устанавливает ERROR и completedAt.
- Отдельный scheduler каждого сервиса раз в 10 секунд проверяет оба хранилища. PROCESSING с processingStartedAt строго раньше `now - 60 секунд` восстанавливается с паузой 10 секунд либо становится ERROR при attempts >= 3.
- Завершение и восстановление проверяют статус и номер попытки; старый обработчик не завершит новую попытку. Результат outbox неизменяем.
- Каждую минуту OK/ERROR с completedAt <= `now - 1 час` очищаются до ID и статуса. В PostgreSQL остальные столбцы становятся SQL NULL, в MongoDB удаляются. Tombstone хранится бессрочно. Незавершённые записи не очищаются.

## Принятые ограничения

Нет атомарности между Post и исходящими событиями: падение между записями может оставить частично созданный пост. Обработчик может опубликовать уже сохранённый исходник до окончания записи остальных. Компенсация при исключении выполняется best effort; результат для удалённого Post пропускается.

Нет атомарности между S3, метаданными файлов, outbox и inbox. Если результат ещё не сохранён, повторная обработка может создать новые ID и лишние объекты; новую очистку сирот эта задача не вводит. Если outbox уже существует, восстановление использует его без обработки изображения. Последняя попытка, прерванная после записи результата, может оставить inbox ERROR, однако сохранённый outbox доставляется независимо.

Сбой после confirm до OK может дать повторную доставку. Сбой между переходом Post в READY и SSE может потерять уведомление: SSE не является отдельным outbox. После исчерпания попыток и часовой очистки исходник автоматически не восстановить; Post может остаться незавершённым. Живая, но навсегда зависшая операция удерживает локальный guard до завершения или перезапуска сервиса.

## Переход

Переход выполняет оператор. Старые данные событий MongoDB не сохраняются; отдельная миграция для них не нужна.

1. Остановить приём новых постов. Дождаться завершения старых очередей, фоновых отправок и всех активных событий обоих сервисов. Разобрать оставшиеся PROCESSING/UNPROCESSED до перехода.
2. Остановить оба приложения. Проверить целевые БД. Совместная работа старой и новой версии не поддерживается.
3. Применить SQL-миграцию `apps/main/prisma/migrations/20260919120000_durable_image_events/migration.sql` штатным процессом миграций с явно проверенной конфигурацией БД. Она меняет PK на event_id, добавляет бинарное поле/сроки и nullable-поля, удаляет неиспользуемый updated_at событий, сохраняет существующие записи.
4. Удалить старые коллекции MongoDB `input_events` и `output_events` целиком, вместе с индексами. Новая версия использует пустые коллекции со строковым `_id` и индексами из Mongoose-схем. Удаления только документов недостаточно: старые уникальные индексы по содержимому события тоже должны исчезнуть.
5. Сгенерировать Prisma client, собрать и запустить новую версию. Проверить поток, затем открыть приём постов.
