# Загрузка и обновление аватара

## Согласованный контракт

- Только `PUT /users/my-avatar`, AccessTokenGuard, userId из JWT.
- Multipart: поле `file`, одно изображение JPEG/PNG, размер не более `10 * 1024 * 1024` байт, включая ровно 10 МиБ. MIME и фактический формат проверяются; пустое/повреждённое изображение отклоняется.
- Ответ после сохранения исходника в PostgreSQL outbox: `201 { userId }`. Ответ подтверждает принятие, а не готовность изображения.
- После сохранения новой пары в User: SSE `avatar-updated` с `{ userId }`. Клиент обновляет данные через GET.
- Ошибки размера/формата используют существующий DomainExceptions-формат и сообщение `The photo must be less than 10 Mb and have JPEG or PNG format`.
- DELETE, серверная обрезка и координаты центрирования не входят в задачу. До Save frontend не отправляет PUT.

## Хранение и обработка

В User добавляются nullable JSON-поля avatar и avatarPreview с MediaFile. До первой загрузки GET и профиль возвращают null. Заглушки UsersMapper заменяются чтением User, включая preview автора поста.

Новый входной контракт `avatar.image.process.v1` содержит eventId, userId, имя, MIME, размер и отдельное бинарное тело. Результат `avatar.image.updated.v1` содержит eventId, consumer MAIN, userId, image и preview; оба обязательны. UUID назначается в main и сохраняется на всех этапах.

Используются существующие четыре хранилища событий, существующие scheduler и механика повторов. Добавляются отдельные очереди аватаров `.avatar-images.v1` и `.avatar-images.results.v1`, но обработка общих таблиц/коллекций остаётся единой: события маршрутизируются по type. Устаревшие post-события в MongoDB без type распознаются как post по их текущему контракту.

Consumer сохраняет inbox до ack. Files worker сохраняет AVATAR и AVATAR_PREVIEW через FilesService; текущая обработка: WebP quality 50, preview fit inside 204x204. Полноразмерный аватар сохраняет размеры исходника. Неизменяемый outbox результата создаётся с тем же eventId; публикация ждёт confirm. Main consumer сохраняет inbox, затем scheduler применяет результат: новая пара записывается одним обновлением User, после чего отправляется SSE. Отсутствующий User — успешный пропуск. Повтор результата, уже совпадающего с сохранённой парой, не вызывает SSE.

Старый аватар остаётся в User до готовности новой пары. Ошибка обработки не удаляет старый аватар. Публичного FAILED-события и статуса операции не добавляем.

## Очистка

Существующий ежедневный scheduler получает из User полный список текущих avatar/preview fileId и вызывает отдельную TCP-команду `cleanup-unused-avatar-files`. Files удаляет неиспользуемые AVATAR/AVATAR_PREVIEW старше 24 часов из S3 и MongoDB, затем сироты S3 в точных префиксах `files/AVATAR/` и `files/AVATAR_PREVIEW/`. Текущие файлы не удаляются, даже если старше суток. Сбой чтения списка запрещает запуск очистки; успешно полученный пустой список допустим. При ошибке удаления запись сохраняется для следующего прохода. Нового поручения удаления в outbox нет.

## Принятые ограничения

- Нет защиты от гонки нескольких загрузок: побеждает последний применённый результат.
- Очистка не учитывает незавершённые события: готовый файл старше суток может быть удалён до применения результата в main.
- Нет транзакций, jobs, новых хранилищ и распределённых блокировок; один экземпляр main/files.
- До записи files outbox повтор обработки может оставить лишние объекты; ежедневная очистка удаляет их впоследствии.
- SSE не сохраняется отдельно: сбой после обновления User до emit может потерять уведомление. GET остаётся источником актуальных данных.
- Общие правила событий: три попытки, пауза 10 секунд, восстановление PROCESSING старше минуты, очистка завершённых через час до ID/статуса. ERROR не гарантирует дальнейший повтор.

## Проверки

Локальная бизнес-логика: ограничения файла, сохранение старого аватара при ошибках, полная замена пары, повтор результата, отсутствующий пользователь, SSE после сохранения. Очистка: активные/свежие файлы сохраняются, старые неактивные удаляются, ошибки допускают следующий проход, префиксы не затрагивают посты. Проверки БД проводят на изолированном окружении. Не добавляются тесты доставки между микросервисами и простого делегирования клиенту.
